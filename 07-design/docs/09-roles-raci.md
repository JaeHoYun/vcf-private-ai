# 09 — 역할과 책임 (RACI)

[← 목차로](../README.md)

Private AI 플랫폼을 만들고 운영하는 일은 한 팀이 다 하지 못합니다. 인프라, 플랫폼, 앱, 보안, 데이터가 단계마다 맞물리는데, "이 일은 누가 책임지고 누가 실행하나"가 흐릿하면 의사결정이 지연되고 책임 공백이 생깁니다. 이 문서는 AI 플랫폼 수명주기를 단계로 나눠, 단계마다 어느 역할이 무엇을 맡는지를 한 장의 RACI 표로 정리합니다.

> 이 표는 **출발점(템플릿)** 입니다. 조직마다 팀 경계와 이름이 다르므로, 자기 조직의 실제 팀에 매핑해 조정해 쓰십시오. 특정 기업의 조직도를 전제하지 않습니다.

---

## 9.1 역할과 RACI 표기

이 문서는 다섯 역할을 가정합니다. 실제 조직에서는 한 팀이 여러 역할을 겸하거나, 한 역할이 여러 팀에 나뉠 수 있습니다.

| 역할 | 맡는 범위 | 주로 맞닿는 시리즈 편 |
|------|-----------|----------------------|
| **인프라** | VCF, vSphere, 네트워크, 스토리지, GPU 하드웨어 | ① |
| **플랫폼** | PAIF, PAIS, VKS, 모델 서빙 플랫폼 | ①③, 앱 가이드(플랫폼 측) |
| **앱** | RAG, 에이전트 애플리케이션, 게이트웨이(BFF, 프런트 전용 백엔드) | ④, 앱 가이드(앱 측) |
| **보안과 거버넌스** | 보안 정책, 격리, 감사, 컴플라이언스 | ⑤ |
| **데이터** | 데이터 준비, 벡터DB 콘텐츠, 문서 접근권한(ACL) | ②⑤(데이터 측) |

RACI는 각 단계에서 역할이 갖는 관여 방식을 네 글자로 표기합니다.

- **R(Responsible, 실행)** — 실제로 그 일을 수행한다.
- **A(Accountable, 책임)** — 결과에 대한 최종 책임과 승인 권한을 가진다. 단계마다 **한 역할**에만 둔다.
- **C(Consulted, 협의)** — 진행 전 의견을 구한다(양방향).
- **I(Informed, 통보)** — 결과를 통보받는다(일방향).

## 9.2 수명주기 RACI

각 단계는 시리즈의 해당 편과 연결됩니다. 단계별로 **A는 하나**이며, A를 가진 역할이 실행(R)까지 겸하는 경우 `A, R`로 표기합니다.

| 단계 (시리즈 편) | 인프라 | 플랫폼 | 앱 | 보안과 거버넌스 | 데이터 |
|------------------|:------:|:------:|:--:|:------------:|:------:|
| 요구사항과 설계 (⑦, ⑥) | C | A, R | C | C | C |
| 인프라와 GPU 구축 (①) | A, R | C | I | C | I |
| 서빙 플랫폼 구축 (①③) | C | A, R | I | C | I |
| 데이터와 벡터DB 구축 (②) | I | C | C | C | A, R |
| RAG, 에이전트 앱 (④, 앱 가이드) | I | C | A, R | C | C |
| 보안, 격리, 거버넌스 (⑤) | C | C | C | A, R | C |
| 에이전트 거버넌스와 게이트 심사 (⑤ 08, 앱 가이드 12) | I | C | R | A | C |
| 운영과 Day-2 (①, ⑦) | R | A | C | C | C |
| 평가와 가드레일 (④, 앱 가이드 13 평가와 가드레일) | I | C | R | A | C |

표를 가로로 읽으면 "이 단계는 누가 책임지고 누가 거드는가"가, 세로로 읽으면 "이 역할은 수명주기 전체에서 언제 전면에 서는가"가 보입니다. 예컨대 보안과 거버넌스는 대부분 단계에서 C로 관여하다가 보안, 격리, 거버넌스 단계와 에이전트 거버넌스, 평가, 가드레일에서 A로 전면에 섭니다.

### 9.2.1 다섯 역할 밖의 승인과 자문 주체

다섯 역할은 플랫폼을 만들고 운영하는 팀입니다. 그런데 몇 단계에는 이 다섯 팀 안에 없는 주체의 승인이 필요하고, 그 주체가 비어 있으면 게이트가 형식이 됩니다. 조직에 맞게 이름을 바꾸되 자리는 비우지 마십시오.

| 주체 | 어디에 관여하나 | 관여 방식 |
|------|-----------------|-----------|
| **법무와 지식재산** | 모델과 데이터셋 라이선스 검토([⑤ 04 4.2절](../../05-security/docs/04-airgap-supply-chain.md)), 고영향 AI 해당 여부 판정, AI 생성물 표시 의무의 적용 범위([앱 가이드 11 11.6절](https://github.com/JaeHoYun/vcf-private-ai-apps/blob/main/docs/11-app-integration-ux.md)) | 반입 게이트와 출시 심사에 C, 해당 여부 판정에 A |
| **AI 위험관리 책임자** | 유스케이스 위험 등급과 자율성 상한의 승인([앱 가이드 02 2.9절, 2.10절](https://github.com/JaeHoYun/vcf-private-ai-apps/blob/main/docs/02-use-cases.md)), 게이트 심사, 에이전트 레지스트리의 소유([⑤ 08 8.4절](../../05-security/docs/08-agent-governance.md)) | 위험 등급과 승격 심사에 A. 개발 조직과 독립시키는 것이 금융권 가이드라인의 요구 |
| **데이터 오너** | 데이터 소스 인입 승인, 보호 문서 복호화 승인([⑤ 05 5.9절](../../05-security/docs/05-data-governance.md), [앱 가이드 06 6.6절](https://github.com/JaeHoYun/vcf-private-ai-apps/blob/main/docs/06-data-onboarding.md)), 권한 회수 통보 | 소스 승인에 A, 데이터 역할이 R로 실행 |
| **개인정보 보호 책임자** | 개인정보 포함 소스의 영향평가, 대화 데이터 보존과 열람 삭제 경로([⑤ 05 5.10절](../../05-security/docs/05-data-governance.md)) | 개인정보가 닿는 단계에 C, 영향평가에 A |

## 9.3 사용법과 주의

- **A는 단계마다 하나로 유지합니다.** A가 둘이면 책임이 갈리고, 없으면 의사결정이 멈춥니다. 조직에 맞게 옮기되 이 규율은 지키십시오.
- **역할명을 자기 조직 팀에 매핑하십시오.** "플랫폼 팀"이 없다면 그 책임이 인프라와 앱 중 어디로 가는지를 먼저 정합니다. 9.2.1의 승인 주체도 마찬가지로, 전담 조직이 없으면 누가 그 서명을 하는지를 정합니다.
- **단계 경계는 시리즈 편과 느슨하게 대응**하므로, 상세 활동은 각 편으로 들어가 확인합니다(예: 격리 통제는 [⑤ 보안과 거버넌스](../../05-security/README.md), 사이징은 [⑥ 사이징, 용량, 비용](../../06-sizing-cost/README.md)).
- 이 표는 책임의 밑그림이며, 실제 운영에서는 변경 관리, 온콜, 승인 흐름 같은 세부 절차로 보강해야 합니다.
