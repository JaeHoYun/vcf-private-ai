# 08 — 레퍼런스 시나리오 (전 과정 예제: 입력 → GPU → 노드 → 클러스터 → 스토리지 → TCO)

> 기반 버전은 [README 버전 기준 문서](../README.md#기반-버전-source-of-truth)를 참조하세요.
> 시리즈 인덱스: [시리즈 허브](../../README.md)

이 문서는 01–07의 산식을 **하나의 시나리오로 처음부터 끝까지** 실행해 보이는 예제입니다. 흩어진 예시 숫자가 아니라, 같은 가정이 입력에서 수량까지 끊김 없이 이어지도록 구성했습니다. 각 단계의 숫자 옆에는 근거가 된 본문 절을 링크해 **추적 가능**하게 둡니다. 같은 계산은 [계산 워크북](../worksheet/README.md)으로 그대로 재현할 수 있습니다.

> **중요 — 이 예제의 숫자는 "예산 추정용 1차 값"입니다.** 성능 작동점은 특정 모델과 GPU의 공개 측정값([부록 A1](../appendix/A1-first-order-reference.md))이고, 1인당 질의 수와 피크/평균비는 근거 없는 가정값입니다. 확정 사이징은 [06.5 PoC→파일럿→프로덕션](06-capacity-planning.md#65-poc--파일럿--프로덕션-용량-로드맵) 실측으로 갈음해야 합니다. 금액(단가)은 본 시리즈 원칙에 따라 제시하지 않으며 견적으로 채웁니다.

## 8.0 시나리오 정의

| 항목 | 값 |
|---|---|
| 용도 | 사내 임직원 대상 **한국어 사내문서 RAG 챗봇**(규정과 기술문서 Q&A) |
| 대상 | 도구를 배포받는 임직원 약 **5,000명** |
| 색인 범위 | 전사 차원에서 고른 지식베이스, 약 10만 문서([05.2](05-storage-network-sizing.md#52-벡터-인덱스-용량--dsm-pgvector-산정-②-연계)) |
| 배포 | 온프레미스(데이터 주권), VCF 9.1.1 / PAIF 9.1.1 / PAIS 3.0, VKS, 통합형 배치([04 4.1절](04-vks-cluster-sizing.md#41-vks-클러스터-토폴로지-개요)) |
| 단계 | 구매 전 예산 산정 → 이후 PoC로 실측 |
| 워크로드 분류 | RAG = 추론 + 임베딩 + 벡터 검색(본문 [01.2](01-sizing-methodology.md#12-워크로드-분류와-자원-특성)) |

이 시나리오의 결론을 먼저 말하면: **1인당 질의가 5–10회인 구간에서는 부하가 아니라 가용성 규칙(복제본 최소 2개)과 PAIF 최소 GPU 호스트 3대가 장비 규모를 정합니다. 질의가 20회로 늘면 복제본과 GPU 호스트가 하나씩 늘어납니다.** GPU 수를 가장 크게 좌우하는 것은 모델 규모와 "지연 목표를 지키는 복제본당 동시성"이므로, 이 예제의 숫자보다 계산 순서를 가져가시기 바랍니다.

**모델 선택에 대해.** 한국어 사내 문서 RAG의 기본값은 중형(M, 24–35B)이지만([A2.4](../appendix/A2-inputs-and-defaults.md#a24-모델-선택-1차-가이드)), 이 규모를 대화형 조건에서 잰 신뢰할 만한 공개 측정이 없어 **공개 측정이 있는 70B dense 모델**(FP8)로 계산했습니다. 70B dense는 메모리로는 중형보다 크고, 필요한 GPU 수는 대형 효율 MoE(L)와 비슷한 쪽입니다. 자사 산정에서는 PoC에서 잰 모델과 작동점으로 바꿔 넣습니다.

## 8.1 단계 1 — 워크로드와 토큰 입력

[부록 A2.1 환산 사슬](../appendix/A2-inputs-and-defaults.md#a21-사업-언어--사이징-입력-환산)로 "5,000명"을 피크 초당 요청으로 환산합니다. 1인당 질의 수는 공개 근거가 없으므로 **5, 10, 20회 세 경우**로 계산해 결과가 얼마나 달라지는지 봅니다.

| 단계 | 가정 | 계산 | 결과(질의 5 / 10 / 20회) |
|---|---|---|---|
| 배포 인원 N | — | — | 5,000 |
| 일 활성 비율 d | 30%(배포 인원 기준 참고 범위 안의 가정) | 5,000 × 0.30 | 1,500 |
| 1인당 질의 q | 5, 10, 20회(가정값. 공개 근거 없음, 자사 실측으로 대체) | 1,500 × q | 7,500 / 15,000 / 30,000 요청/일 |
| 피크 초당 요청 | H=8h, p=3(p는 실측 전 보수 가정) | 일 요청 ÷ 28,800 × 3 | 약 0.78 / 1.56 / 3.13 |

동시 요청 수는 요청당 처리 시간을 알아야 나오므로 8.3에서 계산합니다.

토큰과 모델, 지연 목표 입력([부록 A2.2, A2.3, A2.5](../appendix/A2-inputs-and-defaults.md#a22-워크로드-프로파일-프리셋)):

| 입력 | 값 | 근거 |
|---|---|---|
| 입력 토큰 | 시스템 500 + 질문 100 + 대화 이력 400 + 청크 512 × 6 = **약 4,072** | 입력 계산식(A2.2) |
| 출력 토큰 | **500** | 보수 산정. 평균 산정이면 250–300(A2.2) |
| 한국어 계수 | 1.0 | 위 토큰을 한국어 기준으로 셌다고 가정. 영어 기준 어림이면 1.3–1.7을 곱함 |
| 후보 모델 | **70B dense**, 가중치 FP8, KV 캐시 BF16 | 구조값 레이어 80, KV 헤드 8, head_dim 128(Llama 3.1 70B `config.json`) |
| 복제본 구성 | 복제본 하나에 **H100 80GB 4장**(텐서 병렬 4, NVLink) | 서비스 유형 N2([04 4.3절](04-vks-cluster-sizing.md#43-노드-사양-산정-노드-크기-vs-노드-수)) |
| 지연 목표 | 첫 토큰 2초 이하, 토큰 간 지연 100ms 이하 | [A2.3](../appendix/A2-inputs-and-defaults.md#a23-지연과-가용성-sla-기본값) |
| 가용성 | N+1, 모델 엔드포인트 복제본 최소 2 | A2.3 |

## 8.2 단계 2 — 복제본 하나의 GPU 메모리 (본문 02 적용)

복제본 하나(H100 4장)에 모델과 KV 캐시가 들어가는지, 몇 요청까지 메모리에 담을 수 있는지 확인합니다.

| 항목 | 계산 | 결과 |
|---|---|---|
| 가중치 | 70B × 1바이트(FP8) | 약 70GB |
| 복제본 가용 메모리 | 4 × 80GB × 0.9 − 4 × 4GB(오버헤드) | 약 272GB |
| GPU 메모리 ÷ 가중치 | 320 ÷ 70 | 약 4.6배(점검값 2.5배 이상, [02 2.1절](02-gpu-sizing.md#21-vram-산정의-3대-구성요소)) |
| 토큰당 KV 캐시 | 2 × 80(레이어) × 8(KV 헤드) × 128(head_dim) × 2(BF16) | 327,680바이트 ≈ 0.000305 GiB([A1](../appendix/A1-first-order-reference.md#a11-추론-처리량과-동시성-1차-가정치)의 70B 계수와 일치) |
| 요청당 KV 캐시 | 0.000305 × 4,572토큰 | 약 1.4 GiB |
| 메모리로 담을 수 있는 동시성 | (272 − 70) ÷ 1.4 | 약 144요청 |

메모리만 보면 복제본 하나가 140여 요청을 담을 수 있습니다. 실제 한도는 메모리가 아니라 **지연 목표**가 정하므로 다음 단계에서 성능 작동점을 봅니다.

## 8.3 단계 3 — 성능 작동점과 복제본 수 (본문 02.5, 부록 A1, A2.3)

NVIDIA가 공개한 같은 구성(70B FP8, H100 4장, 입력 5,000토큰, 출력 500토큰)의 측정값입니다([부록 A1.1](../appendix/A1-first-order-reference.md#a11-추론-처리량과-동시성-1차-가정치)).

| 동시성 | 첫 토큰 시간 | 토큰 간 지연 | 요청당 처리 시간(계산) |
|---|---|---|---|
| 1 | 0.24초 | 17.35ms | 약 8.9초 |
| 25 | 0.66초 | 28.69ms | 약 15.0초 |
| 50 | 0.95초 | 40.13ms | 약 21.0초 |
| 100 | 1.31초 | 68.86ms | 약 35.7초 |

요청당 처리 시간 = 첫 토큰 시간 + 토큰 간 지연 × 출력 토큰 수입니다([A2.3](../appendix/A2-inputs-and-defaults.md#a23-지연과-가용성-sla-기본값)).

**작동점 선택.** 네 측정 모두 지연 목표(첫 토큰 2초, 토큰 간 100ms)를 넘지 않으므로 목표만 보면 동시성 100까지 쓸 수 있습니다. 그러나 공개 측정은 평균값이라 백분위 목표와 차이가 있고, 한국어 응답이 길어질 여유도 필요합니다. 그래서 **토큰 간 지연 50ms 이하(초당 20토큰 이상)인 가장 높은 동시성인 50**을 복제본당 작동점으로 고르고, 이때 요청당 처리 시간 **약 21초**를 씁니다. 측정 조건(입력 5,000토큰)이 이 시나리오(약 4,072토큰)보다 약간 무거워 보수적인 쪽입니다. 이 값은 NIM 엔진 기준이며 다른 엔진(vLLM 등)이나 엔진 버전에서는 달라집니다.

| 항목 | 질의 5회 | 질의 10회 | 질의 20회 | 계산 |
|---|---|---|---|---|
| 피크 동시 요청 | 약 16.4 | 약 32.8 | 약 65.6 | 피크 초당 요청 × 21초 |
| 설계 동시성(+30% 버스트) | 22 | 43 | 86 | 올림 |
| 부하를 받는 복제본 | 1 | 1 | 2 | 설계 동시성 ÷ 50, 올림 |
| 총 복제본 | 2 | 2 | 3 | N+1, 최소 2 |
| 추론 GPU | 8 | 8 | 12 | 복제본 × 4 |
| 임베딩과 리랭커 GPU | 1 | 1 | 1 | [03 3.5절](03-compute-memory-sizing.md#35-임베딩과-리랭커-서버-사이징rag-비-llm-컴포넌트). CPU로 돌리면 0 |
| **사용 GPU 합계** | **9** | **9** | **13** | |

- 질의 5회와 10회의 결과가 같습니다. 부하는 복제본 하나로 충분하지만 가용성 규칙이 복제본 2개를 요구하기 때문입니다.
- 실제 동시성이 작동점(50)보다 낮으면 요청당 처리 시간은 21초보다 짧으므로 이 계산은 보수적으로 잡힌 값입니다.

## 8.4 단계 4 — 물리 호스트와 클러스터 (본문 04 적용)

복제본(4장)이 호스트 하나 안에서 NVLink로 묶이도록 **호스트당 GPU 4장** 서버를 가정합니다.

| 항목 | 질의 5, 10회 | 질의 20회 | 근거 |
|---|---|---|---|
| GPU 호스트 | 3대 | 4대 | MAX(사용 GPU ÷ 4 올림, PAIF 최소 3대)([01.1](01-sizing-methodology.md#11-사이징의-목적과-본-가이드의-위치)) |
| 장착 GPU | 12장 | 16장 | 호스트 × 4 |
| 여유 GPU | 3장 | 3장 | 신규 워크로드나 장애 대비 |
| 호스트당 RAM 출발값 | 640–960GB | 640–960GB | GPU 메모리 합 320GB의 2–3배([03 3.1절](03-compute-memory-sizing.md#31-gpu-노드의-비-gpu-자원-vcpu-메모리-비율)) |

VKS 클러스터 노드([04.6 사이징 워크시트](04-vks-cluster-sizing.md#46-인프라-고려사항과-사이징-워크시트)):

| 항목 | 질의 5, 10회 | 질의 20회 | 근거 |
|---|---|---|---|
| GPU 워커 노드 | 3(복제본 2 + 임베딩 1) | 4(복제본 3 + 임베딩 1) | 복제본당 노드 1개, [04 4.3절](04-vks-cluster-sizing.md#43-노드-사양-산정-노드-크기-vs-노드-수) |
| GPU 워커 오토스케일 상한(+20%) | 4 | 5 | [04.4](04-vks-cluster-sizing.md#44-오토스케일-헤드룸-버스트-스케일-지연) |
| 일반 워커 노드 | 3 | 3 | 시스템 애드온과 CPU 경로 |
| 컨트롤 플레인 | 3 | 3 | HA(홀수) |
| **클러스터 노드 합계** | **10 VM** | **11 VM** | |
| Supervisor 한도 점검 | 여유 | 여유 | [04.5](04-vks-cluster-sizing.md#45-스케일-한도와-단일-대형-vs-다중-클러스터-설계) |

이 예제는 **통합형 배치**를 따라 컨트롤 플레인과 일반 워커 VM도 GPU 호스트에 함께 둡니다. 따라서 물리 호스트는 질의 5, 10회에 3대, 20회에 4대이며 8.6의 라이선스 코어는 이 호스트들의 물리 코어 합입니다. 컨트롤 플레인과 일반 워커를 GPU가 없는 호스트 3대에 따로 두는 분리형이면 물리 호스트와 라이선스 코어가 그만큼 늘어납니다.

이 시나리오의 교훈: **소규모에서는 PAIF 최소 GPU 호스트 3대와 최소 복제본 2개가 장비 규모를 정하고, 부하가 일정 수준을 넘어야 호스트가 늘어납니다.** 호스트 한 대가 멈추면 복제본 하나가 빠지므로, N+1 복제본이 그 부하를 받는지 파일럿에서 확인합니다.

> HA 단계화: PoC, 파일럿은 단일 vSphere Zone, 3 호스트로 시작하고, 프로덕션 HA가 필요하면 3-Zone(Zone당 최소 3 호스트)으로 확장합니다([04.1](04-vks-cluster-sizing.md#41-vks-클러스터-토폴로지-개요)). PAIS는 단일 Zone 구성을 권장하므로 다중 Zone의 이점은 제한됩니다. GPU 노드 오토스케일은 부팅과 드라이버 기동 지연이 크므로 min에 헤드룸을 둡니다([04.4](04-vks-cluster-sizing.md#44-오토스케일-헤드룸-버스트-스케일-지연)).

GPU Operator 데몬셋 오버헤드(노드당 상시 vCPU, RAM)는 노드 가용 자원에서 차감해야 합니다([04.3](04-vks-cluster-sizing.md#43-노드-사양-산정-노드-크기-vs-노드-수)).

## 8.5 단계 5 — 스토리지 용량 (본문 05 적용)

[05.5 워크시트](05-storage-network-sizing.md#55-사이징-워크시트--규모에서-용량으로)에 대입합니다. 가정: 전사 큐레이션 약 10만 문서에서 벡터 280만 건(색인 범위 시나리오의 상단, [05.2](05-storage-network-sizing.md#52-벡터-인덱스-용량--dsm-pgvector-산정-②-연계)), 1536차원, 원문 저장 용량 100GB(문서당 약 1MB로 둔 가정), 모델 FP8 가중치 3버전 보존.

| 갈래 | 논리 용량(어림) | 근거 |
|---|---|---|
| 모델 아티팩트 | 70GB × 3버전 ≈ 210GB | [05.1](05-storage-network-sizing.md#51-스토리지-용량--어디에-무엇이-쌓이는가) |
| 컨테이너 이미지 | 약 50GB(확인 필요) | 05.1 |
| 원문과 전처리 사본 | 100GB × 1.5 ≈ 150GB | 05.1 |
| 벡터 인덱스(pgvector) | 원시 약 16GB + HNSW 약 32GB ≈ 48GB | 05.2 |
| 로그와 관측 | 약 30GB | 05.1 |
| **논리 합계(구성요소 합산)** | **약 488GB** | 합산 |
| **필요 가용 용량** | × 1.5(보호 오버헤드) ≈ **약 0.73TB** | [05.3](05-storage-network-sizing.md#53-스토리지-성능--모델-로딩과-iops) |

**공식 비율로 교차 점검.** Broadcom 설계 권장(RAG 벡터 DB 저장 용량은 원문의 5–10배)을 적용하면 원문 100GB에 약 0.5–1TB입니다. 원문과 벡터 자리에 상한 1TB를 넣으면 논리 합계는 약 1.29TB, 필요 가용 용량은 **약 1.9TB**입니다. 구성요소 합산(원문과 벡터 약 198GB)과 차이가 큰 것은 벡터 수와 원문 용량을 서로 독립적으로 가정했기 때문이므로, 예산은 **약 1.9TB를 상한**으로 두고 문서 표본 실측으로 좁힙니다([05.5](05-storage-network-sizing.md#55-사이징-워크시트--규모에서-용량으로)).

또한 **HNSW 인덱스는 검색 성능을 위해 RAM 상주가 권장**되므로 벡터 DB 메모리 사이징과 직결됩니다([05.2](05-storage-network-sizing.md#52-벡터-인덱스-용량--dsm-pgvector-산정-②-연계)). 70GB급 모델의 콜드스타트는 로더 방식에 따라 수십 초 규모입니다([A1.3](../appendix/A1-first-order-reference.md#a13-모델-콜드스타트와-로딩-1차-가정치)).

## 8.6 단계 6 — TCO 수량 골격 (본문 07 적용)

[07](07-tco-cost-model.md)의 분해에 사이징 결과를 넣습니다. **단가는 비우고**(견적), 수량만 채웁니다.

| 대분류 | 수량(질의 5, 10회 / 20회) | 단가 |
|---|---|---|
| VCF 코어 구독 | 물리 호스트 3대 / 4대 × 호스트당 64코어(예시 사양, 소켓당 최소 16코어 규칙 반영) = 192 / 256코어 | (견적) |
| NVAIE(GPU당) | 장착 GPU 12 / 16장. 성능 작동점이 NIM 측정값이므로 NIM 사용을 가정 | (NVIDIA 견적) |
| DSM(Data Services Manager) | VCF 포함 권한(벡터 DB용 pgvector) | (조건 확인) |
| GPU 하드웨어 | 장착 GPU 12 / 16장 ÷ 상각연수 | (견적) |
| GPU 서버 | 3 / 4대(호스트당 GPU 4장, NVLink) | (견적) |
| 스토리지, 네트워크 | 가용 약 0.73–1.9TB, 스위치 | (견적) |
| OpEx | 전력(장착 GPU 소비전력 × PUE), 상면, 운영 FTE(선택, 국내는 보통 제외) | (사이트 데이터) |

산정 함정 점검([07.2](07-tco-cost-model.md#72-소프트웨어-라이선스구독-비용)):

- PAIF는 VCF 구독에 포함 → 별도 제품으로 **이중 계상 금지**.
- NVAIE는 **GPU 할당 방식과 소프트웨어에 따라 필요 여부가 갈립니다.** NIM이나 vGPU를 쓰면 서버에 장착된 물리 GPU 전수가 대상이고, DirectPath 전용 할당과 오픈소스 추론 엔진만 쓰면 필요하지 않습니다. 이 경우 성능 작동점은 그 엔진으로 다시 재야 합니다.
- VCF 코어는 사이징 물리 코어를 그대로 쓰지 말고 **코어 최소수량 규칙** 반영.
- 하드웨어와 전력은 **사용 GPU(9, 13장)가 아니라 장착 GPU(12, 16장)** 기준입니다.

> 빈 단가 칸을 채우는 방법(무엇을 견적 요청할지)은 부록 A3(RFQ 체크리스트)에서 다룹니다. 퍼블릭 클라우드와의 손익분기 개념은 [07.6](07-tco-cost-model.md#76-퍼블릭-gpu-클라우드-vs-온프레미스-paif-비교-프레임)을 참조하세요.

## 8.7 결과 요약과 다음 행동

| 산출물 | 질의 5, 10회 | 질의 20회 | 확정 경로 |
|---|---|---|---|
| 설계 동시성 | 22 / 43 | 86 | 파일럿 실측([06.5](06-capacity-planning.md#65-poc--파일럿--프로덕션-용량-로드맵)) |
| 모델과 복제본 | 70B FP8, 복제본 2개 | 복제본 3개 | PoC 품질 평가와 작동점 실측 |
| 사용 GPU / 장착 GPU | 9 / 12장 | 13 / 16장 | PoC 작동점 실측 |
| GPU 호스트 / 클러스터 노드 | 3대 / 10 VM | 4대 / 11 VM | 04.7 실측 |
| 스토리지 | 가용 약 0.73–1.9TB | 가용 약 0.73–1.9TB | 05.6 표본 실측 |
| TCO 수량 | 코어 192, NVAIE 12 | 코어 256, NVAIE 16 | 07.8 견적 |

### 이 예제가 보여주는 것

1. **계산 순서는 결정론적이다.** 입력(A2) → 처리 시간과 동시성 → 복제본 → 호스트 → 노드(04) → 스토리지(05) → 수량(07)이 끊김 없이 이어집니다.
2. **소규모에서는 규칙이 규모를 정한다.** 질의 5회와 10회의 결과가 같습니다. 최소 복제본 2개와 PAIF 최소 GPU 호스트 3대 때문입니다. 부하가 규모를 정하기 시작하는 지점을 알아야 증설 시점을 계획할 수 있습니다.
3. **가장 큰 변수는 모델과 성능 작동점이다.** 같은 사용자 수라도 모델 규모, 엔진, GPU, 작동점 동시성에 따라 복제본당 GPU와 복제본 수가 몇 배씩 달라집니다. 그래서 PoC에서 가장 먼저 잴 값은 "지연 목표를 지키는 복제본당 동시성"입니다.

> 다음 행동은 **PoC**입니다([06.5.1](06-capacity-planning.md#651-poc-형태--형태가-검증-범위를-정한다)의 형태 (다) 권장). 한국어 사내 문서 RAG 기본값인 중형(M)과 인접 유형 후보를 자사 질문과 문서로 품질 평가하고, 고른 모델의 작동점(지연 목표를 지키는 동시성, 그때의 첫 토큰 시간과 토큰 간 지연)을 잰 뒤, [계산 워크북](../worksheet/README.md)의 입력을 실측값으로 바꿔 8.1부터 다시 계산하세요.
