# 04 자산 처분 결정 매트릭스 (6R)

> 이 워크시트는 [문서 08 — 브라운필드 통합 설계](../docs/08-brownfield-integration.md) 8.5절의 판정을 자산 단위로 기록하는 양식입니다. AX 방법론 가이드가 착수 전 단계의 안내로 재편되면서 그쪽에 있던 양식을 이 시리즈로 옮겨 왔습니다.

이 문서는 이미 운영 중인 AI 자산을 자산 단위로 검토하여, 무엇을 남기고(잔류) 무엇을 옮기고 온프렘 회귀하고 통합하고 재구성하거나 폐기할지를 근거에 묶어 결정하기 위해 직접 작성하는 양식입니다. 6R은 자산을 처분(disposition)하는 여섯 가지 행동 선택지를 가리키며, 클라우드 마이그레이션 분야에서 쓰이는 6R 분류를 AI 인프라 자산에 맞게 변형한 것입니다.

## 머리말 — 누가, 언제, 채운 뒤 어디에 쓰는가

- **누가**: 인프라 운영 책임자와 재무와 보안 검토자가 공동으로 채웁니다. 각 자산의 단가와 가동률은 운영 책임자가, 데이터 민감도, 주권은 보안, 법무 검토자가 출처를 댑니다.
- **언제**: [03 자산 인벤토리](03-ai-estate-inventory.md)를 1차 완료한 직후 채웁니다. 인벤토리가 비어 있으면 이 매트릭스는 근거 없는 추정이 되므로 선행 입력을 먼저 확보합니다.
- **채운 뒤**: 자산별 6R 결정과 그 근거는 [문서 08 8.6절](../docs/08-brownfield-integration.md)의 통합 시퀀스를 짜는 입력이 되고, 온프렘 회귀와 통합과 재구성으로 분류된 자산은 [02 설계 결정 기록](02-design-decision-record.md)의 전제가 됩니다. 정량 수치 자체는 이 양식에서 계산하지 않고, 외부 사이징과 비용 시리즈 워크북의 산출값을 옮겨 적습니다.

### 방향 — 역방향(기존 자산 감사와 정리)

이 양식은 이미 보유한 AI 자산을 감사하여 정리하는 역방향 동선입니다. 새로 지을 환경의 요구사항을 모으는 전방 동선의 [01 결정 요인 시트](01-driver-sheet.md)와 방향이 반대이므로, 두 양식을 혼용하지 않습니다.

### 빅뱅 회귀 경계

이 매트릭스는 "전사 청사진을 먼저 그린 뒤 한꺼번에 갈아엎으라"는 양식이 아닙니다. 온프렘 회귀, 통합, 폐기는 인벤토리 실측과 검증된 수요가 있을 때 자산 단위로 진화적으로 진행하는 결정이며, 이 점이 어긋나면 [문서 08 8.7절](../docs/08-brownfield-integration.md)이 경고하는 일괄 온프렘 회귀의 함정으로 되돌아갑니다.

## 1. 처분 6R 정의 (AI 자산용 변형)

| 코드 | 행동 | AI 자산 맥락의 의미 |
|---|---|---|
| Retain | 잔류 | 베어메탈 GPU 등 현 위치와 현 형태를 그대로 유지. 손대지 않는 것이 합리적인 자산 |
| Relocate | 이전 | 형태는 유지하되 위치만 옮김(예: 리전 이동, 코로케이션 이전) |
| Repatriate | 온프렘 회귀 | 퍼블릭 클라우드에서 프라이빗과 온프렘으로 되가져옴 |
| Consolidate | 통합 | 중복과 분산된 자산을 하나로 합침(중복 AI팀과 중복 추론 엔드포인트 등) |
| Refactor | 재구성 | 형태와 아키텍처를 바꿔 다시 구성(예: 공유 스케줄러 도입, 모델 서빙 계층 교체) |
| Retire | 폐기 | 더 이상 수요가 없거나 가치가 비용을 밑도는 자산을 종료 |

용어 풀이: **잔류**(Retain)는 "옮기지 않는다"는 적극적 결정이지 "아직 손대지 못했다"는 방치가 아닙니다. 두 상태를 구분해 기록합니다.

## 2. 자산별 6R 선택 표

한 행이 한 자산입니다. 자산 ID와 명칭은 [인벤토리](03-ai-estate-inventory.md)의 식별자를 그대로 옮겨 적어 추적이 끊기지 않게 합니다. 현재 위치와 형태와 서비스 형태 분류도 인벤토리에서 인용하며, 기준은 인벤토리이고 갱신 책임도 인벤토리에 둡니다(인벤토리가 바뀌면 이 표를 따라 갱신). 6R 열에는 최종 선택 하나만 표기하고, 후보가 둘 이상이면 비고에 차순위와 보류 사유를 적습니다.

| 자산 ID | 자산 명칭과 유형 | 현재 위치와 형태 | 6R 선택 | 핵심 근거(요약) | 결정 신뢰도 | 비고(차순위, 전제, 재검토) |
|---|---|---|---|---|---|---|
| (인벤토리 ID) | (예: 추론 엔드포인트 A) |  |  |  | 상/중/하 |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

위 표의 빈칸은 채우라고 비워둔 것입니다. 자산 수만큼 행을 늘립니다.

- **6R 선택** [필수]: 위 6코드 중 하나. 출처는 아래 3절 스코어링 결과와 4절 흐름.
- **핵심 근거** [필수]: 어떤 점수와 판정이 이 선택을 끌어냈는지 한두 줄. 결정을 끈 축과 그 등급을 반드시 병기해 채점→결정의 추적이 끊기지 않게 합니다(예: "데이터 주권 5 → 잔류"). 측정 방법은 해당 점수 항목 출처를 가리킴.
- **결정 신뢰도** [권장]: 입력 데이터의 충분성에 대한 자기 평가(상/중/하). '하'인 행은 추가 실측 과제로 분리(6절).
- **비고** [선택, 단 일부 조건부 필수]: 차순위 R, 결정의 전제 조건, 재검토 시점과 트리거. 재검토 시점과 트리거는 결정 신뢰도 '중과 하' 행과 온프렘 회귀와 이전 후보 행에 한해 필수로 적습니다(예: "사용 패턴 12개월 누적 시", "클라우드 단가 X% 변동 시"). 그 외 행에서는 선택입니다.

## 3. 스코어링 가이드

각 자산을 다섯 축으로 채점합니다. 점수는 1–5 정수이며, 자동 계산은 없습니다. 정량 축(단가 손익분기, 재작성, 이전 비용)의 원수치는 외부 사이징과 비용 워크북에서 옮겨 적고, 이 표에는 그 수치를 1–5로 환산한 등급만 기록합니다.

| 스코어링 축 | 1점(이전과 정리 압력 낮음) | 5점(이전과 정리 압력 높음) | 출처와 측정 방법 |
|---|---|---|---|
| 데이터 민감도와 주권 | 공개와 비민감, 위치 제약 없음 | 규제, 주권으로 국내, 온프렘 강제 | 데이터 분류 정책, 법무와 보안 검토 |
| 단가 손익분기 | 클라우드가 단가상 유리 | 자가 보유가 단가상 유리 | 비용 워크북의 GPU 시간당 단가 대비 |
| 재작성과 이전 비용 | 이전이 거의 무비용 | 재작성과 이전 비용이 큼 | 사이징과 이전 견적 워크북 |
| 벤더 종속도 | 표준과 이식 가능 | 특정 벤더 API, 서비스에 강결합 | 아키텍처 실사, 종속 서비스 목록 |
| 사용 패턴 안정성 | 변동과 예측 불가 | 예측 가능과 지속 부하 | 12–24개월 사용량 로그 |

채점값의 다음 활용: 다섯 축 점수는 합산해 단일 순위로 쓰지 않습니다. 축마다 다른 R로 끌기 때문입니다(예: 데이터 주권 5점은 온프렘 회귀와 잔류로, 벤더 종속도 5점은 재구성으로). 점수는 4절 흐름의 분기 입력으로만 쓰며, 결정을 끈 축과 등급은 2절 표의 핵심 근거 칸에 병기해 추적 체인에 남깁니다.

### 점수에서 R로 가는 경향 (단정 아닌 참고)

- 데이터 민감도와 주권 높음 → 온프렘 회귀와 잔류 쪽으로 당김.
- 단가 손익분기에서 자가 보유 유리 + 사용 패턴 안정 → 온프렘 회귀 검토.
- 재작성과 이전 비용 큼 → 잔류나 재구성 쪽으로, 이전이나 온프렘 회귀는 신중.
- 벤더 종속도 높음 → 재구성으로 종속 완화 검토.
- 사용 패턴 안정성 낮음(변동적) → 클라우드 잔류 쪽으로.

## 4. 의사결정 흐름

자산마다 아래 순서로 점검합니다. 각 분기는 단정이 아니라 판단축이며, "예"가 곧 자동 결정은 아니고 다음 절의 온프렘 회귀 판정 기준과 교차 확인합니다.

1. 더 이상 쓰이지 않거나 가치가 운영비를 밑도는가? → 예이면 **폐기(Retire)** 후보.
2. 동일과 유사 기능 자산이 중복되는가(중복 추론 엔드포인트와 중복 AI팀 자산)? → 예이면 **통합(Consolidate)** 후보.
3. 데이터 주권, 지연, 데이터 중력이 데이터의 위치를 강제하는가? → 예이면 데이터가 강제하는 위치로(이미 온프렘이면 **잔류**, 퍼블릭 클라우드에 있으면 **온프렘 회귀**).
4. 서비스 형태가 매니지드 API, 서버리스(요청, 토큰 종량)인가? → 예이면 **잔류**(Retain)가 기본값이며, 5절 온프렘 회귀 판정에서 강한 사유가 확인될 때만 온프렘 회귀로 넘깁니다. 이 분기는 예약 인스턴스로 직접 운영하는 IaaS 자가호스팅 자산에는 적용하지 않습니다.
5. (IaaS 자가호스팅 자산 한정) 퍼블릭 클라우드에 있고 5절 온프렘 회귀 판정에 부합하는가? → 예이면 **온프렘 회귀(Repatriate)** 후보.
6. 형태는 유지하되 위치만 바꾸면 이득인가(리전과 코로케이션)? → 예이면 **이전(Relocate)** 후보.
7. 벤더 종속과 구조 비효율이 큰가? → 예이면 **재구성(Refactor)** 후보.
8. (MLOps 플랫폼 계층 한정) MLOps 플랫폼과 파이프라인 자산(인벤토리 블록 9)인가? → 예이면 의존도가 낮고 상태를 적게 들고 있는 계층부터(레지스트리와 아티팩트 → 파이프라인 → 스케줄러) 옮기는 방침에 따라 처분하며([문서 08 8.4절, 8.6절](../docs/08-brownfield-integration.md)), 통상 **온프렘 회귀**(Repatriate) 또는 **재구성**(Refactor)에 해당합니다.
9. 위 어디에도 강하게 걸리지 않는가? → **잔류(Retain)** — 방치가 아닌 적극적 유지 결정.

여기서 "데이터 중력"(data gravity)은 데이터가 쌓일수록 그 데이터를 옮기기 어려워지고 연산이 데이터 쪽으로 끌려오는 현상을 가리킵니다.

서비스 형태 구분이 4, 5단계 분기를 가릅니다. 매니지드 API, 서버리스는 공유 인프라에 요청과 토큰 단위로 과금되어 유휴 비용이 운영자에게 직접 쌓이지 않으므로 잔류가 기본입니다. 반면 IaaS 자가호스팅은 예약 인스턴스가 모델 가동 여부와 무관하게 시간당 과금되어, 저트래픽 구간의 유휴 비용, 콜드스타트, 이그레스가 온프렘 회귀 검토의 실익을 만드는 자산입니다. 서비스 형태 분류 자체는 [인벤토리](03-ai-estate-inventory.md) 블록 4의 "서비스 형태" 항목을 그대로 옮겨 적습니다.

## 5. 온프렘 회귀(Repatriation) 판정 기준

아래는 온프렘 회귀 여부를 가르는 판단축입니다. 수치는 예시이며 자사 실측으로 갈음합니다. 단정형 기준이 아니라, 여러 축을 함께 보고 온프렘 회귀가 합리적인지 판단하는 잣대로 씁니다.

온프렘 회귀의 기본 자세는 "강한 사유가 있을 때만"입니다. 매니지드 API, 서버리스(요청, 토큰 종량) 자산은 잔류(현행 유지)가 기본값이며, 온프렘 회귀는 아래 판단축 가운데 데이터 주권 같은 강한 사유가 확인될 때만 검토합니다. 온프렘 회귀가 단순한 위치 이동이 아니라 사실상 신규 구축에 가깝기 때문입니다. 작성 시점(2026-06) 기준 일반 논거로는, 온프렘 회귀에 데이터 이그레스 비용, 온프렘 인프라 신규 투자(데이터센터와 네트워킹 포함), 재플랫폼 엔지니어링(흔히 수개월 단위), 전환 중 다운타임 영향이 함께 따른다는 점이 보고됩니다. 적용 전 자사 견적과 최신 공식 자료로 재확인하시기 바랍니다.

- **서비스 형태(매니지드와 서버리스 대 자가호스팅)**: 매니지드 API, 서버리스 자산은 잔류가 기본값이고, 온프렘 회귀는 아래 다른 축에서 강한 사유가 설 때만. 온프렘 회귀 검토의 실익이 큰 쪽은 예약 인스턴스로 시간당 과금되는 IaaS 자가호스팅 자산입니다.
- **지속 가동률 대 손익분기**: 예측 가능한 지속 추론 워크로드는 지속 가동률이 손익분기를 넘으면 온프렘이 유리해질 수 있습니다. 손익분기 가동률은 일반 기준선에 기대지 않고 자사 단가로 계산합니다([⑥ 07 7.6절](../../06-sizing-cost/docs/07-tco-cost-model.md)). 변동, 간헐, 계절성 수요는 요청, 토큰 종량이 예약 용량보다 경제적인 구간이 넓어, 잔류 쪽으로 당겨집니다.
- **회수기간(payback)**: 동일 GPU의 클라우드 연환산 비용을 구매가와 견주어 회수기간을 따집니다. 온프렘 자가 운영의 상시 인력과 조달 리드타임(고성능 GPU는 수 주 단위가 보고됨)도 회수기간에 함께 얹습니다.
- **사용 패턴 성숙도**: 클라우드에서 12–24개월 운영되어 사용 패턴이 예측 가능해졌는지 봅니다.
- **하이브리드 분할**: 변동적 훈련은 클라우드에 유지하고, 지속적 추론은 온프렘으로 가르는 분할이 더 합리적일 수 있습니다. 실무적 절충으로는 상시 고부하 핵심 모델만 전용 GPU에 상주시키고 롱테일 모델은 서버리스에 잔류시키는 방식이 거론됩니다.
- **데이터 중력, 지연, 주권**: 이 셋 중 하나라도 온프렘 회귀를 강제하면 단가와 무관하게 온프렘 회귀가 당겨질 수 있습니다. 매니지드와 서버리스 자산을 온프렘 회귀로 넘기는 "강한 사유"는 대개 이 축에서 나옵니다.

6R 매트릭스와의 정합: 위 기준은 1절 정의의 잔류(Retain, 현 위치와 현 형태를 그대로 유지하는 적극적 결정)와 온프렘 회귀(Repatriate, 퍼블릭 클라우드에서 프라이빗과 온프렘으로 되가져옴)를 가르는 잣대입니다. 매니지드와 서버리스의 기본값 잔류는 1절 잔류 정의의 "손대지 않는 것이 합리적인 자산"에 해당하며, 4절 흐름 4단계와도 맞물립니다.

이 판정 기준의 본문 설명은 [문서 08 8.5.1절, 8.5.2절](../docs/08-brownfield-integration.md)에 있고, 온프렘 회귀 후의 구체 구현(마이그레이션과 통합 실행)은 같은 문서 8.4절과 8.6절이 다룹니다.

## 6. 채운 뒤 연계

- 자산별 6R 결정과 근거는 [문서 08 8.6절](../docs/08-brownfield-integration.md)의 통합 시퀀스에서 무엇을 어떤 순서로 옮길지의 입력이 됩니다.
- 온프렘 회귀, 통합, 재구성으로 분류된 자산이 요구하는 목표 형상은 [02 설계 결정 기록](02-design-decision-record.md)과 [문서 02 블루프린트](../docs/02-reference-blueprints.md)의 선택에 반영합니다. 단일 청사진 하나가 아니라 두세 개 옵션(전량 온프렘 회귀, 하이브리드 유지, 선택적 통합)을 나란히 비교합니다.
- 검증된 수요가 받쳐 주는 항목만 1차 단계의 대상 목록에 올립니다.
- 결정 신뢰도 '하'인 행은 별도의 추가 실측 과제로 분리해, 근거가 갖춰진 뒤 재판정합니다.
- 비용 증거는 [⑥ 부록 A4 AI FinOps 스코어카드](../../06-sizing-cost/appendix/A4-ai-finops-scorecard.md)에서, 민감도와 주권의 근거는 [⑤ 거버넌스와 데이터주권 갭 워크시트](../../05-security/worksheet/governance-sovereignty-gap.md)에서 가져옵니다.
