# 07 — 관측성과 운영

> 기반 버전은 [README 버전 기준 문서](../README.md#기반-버전-source-of-truth)를 참조하세요.

추론 API를 프로덕션에서 운영하려면 가용성, 성능, 비용을 지속적으로 관찰해야 합니다. 이 문서는 추론 API를 프로덕션에서 **무엇으로 관찰하고, 무엇을 조심하는가**를 정리합니다.

---

## 7.1 토큰 사용량 — 응답에 들어 있는 1차 신호

모든 추론 응답의 `usage` 필드가 가장 기본적인 운영 신호입니다. 별도 도구 없이 바로 쓸 수 있습니다.

| 필드 | 의미 | 운영 활용 |
|------|------|----------|
| `prompt_tokens` | 입력 토큰 수 | 프롬프트와 컨텍스트가 과도하게 커지는지 감지(RAG 청크 과다 주입 등) |
| `completion_tokens` | 생성 토큰 수 | 응답 길이와 비용 추적 |
| `total_tokens` | 합계 | 사용량 집계, 내부 과금(쇼백) 기준 |

> 토큰 사용량을 **호출 단위로 로깅**해 두면, 어느 앱, 사용자, 에이전트가 GPU를 많이 쓰는지 사후 분석이 가능합니다. 사내 추론은 종량 청구서가 오지 않으므로, **쇼백(showback)을 직접 만들어야** 부서별 비용 책임이 가시화됩니다.

PAIS 3.0부터는 원격 클라우드 모델([02 2.5.1절](02-serving-api-architecture.md))의 토큰 사용량도 플랫폼이 추적합니다. 이쪽은 사내 GPU와 달리 공급자 청구서가 실제로 오므로, 같은 `usage` 필드라도 의미가 다릅니다. 로컬과 공유 모델의 토큰은 쇼백의 배분 기준이고, 원격 모델의 토큰은 실제 청구 비용인 동시에 반출 증빙입니다. 호출 로그에 모델이 어느 연결 방식인지를 함께 남겨 두어야 둘을 나눠 집계할 수 있습니다.

## 7.2 LLM 트레이싱 (OpenTelemetry)

PAIS는 **OpenTelemetry(OTel) 기반 LLM 트레이싱**을 제공합니다(2.1부터). 에이전트 호출은 검색, 도구 호출, 추론 등 여러 단계를 거치므로, 단계별 추적이 디버깅, 성능, 비용 분석의 핵심입니다.

| 추적 대상 | 확인 가능한 것 |
|----------|--------------|
| LLM 호출 | 토큰 사용량, 지연, 캐시 활용률 |
| RAG 검색 | 검색된 청크, 유사도(Similarity) 점수 |
| MCP 도구 호출 | 호출된 도구, 인자, 결과, 소요 시간 |
| 전체 트레이스 | 한 요청의 end-to-end 단계별 타임라인 |

> **알려진 이슈(PAIS 2.1):** 일부 환경에서 PAIS의 LLM 트레이스가 OpenTelemetry Collector에 표시되지 않을 수 있다고 릴리스 노트에 기재되어 있습니다. 관측성 구성 시 **트레이스 수신을 반드시 검증**하고, 적용 직전 릴리스 노트에서 해당 이슈의 상태를 확인하시기 바랍니다. 3.0 릴리스 노트의 알려진 이슈 목록에는 이 항목이 없지만, 구성 오류로 트레이스가 보이지 않는 경우는 여전히 있으므로 검증 절차는 그대로 둡니다.

PAIS 3.0은 트레이싱 범위를 "LLM 상호작용 전체"로 넓혔다고 밝힙니다. 동작 변경도 하나 있습니다. Prometheus 메트릭 수집이 PAIS가 관리하는 VKS 클러스터가 가용해진 뒤에 시작되므로, 설치나 업그레이드 직후에는 메트릭이 비어 있는 구간이 생깁니다. 이 구간을 장애로 오인하지 않도록 알람 규칙에 유예를 두십시오([① 10 10.2.4절](../../01-infra/docs/10-operations.md)).

## 7.3 Grafana 기반 PAIS 관측성 — 모델 health, quality, behavior

PAIS는 OTel 트레이싱과 더불어 **관측성 프레임워크로 AI 메트릭 대시보드**를 제공합니다(2.1부터). 에이전트에 사용되는 모델의 **health(가용성), quality(품질), behavior(동작)** 을 추적하도록 설계되어 있으며, 메트릭 시각화는 **Grafana**에 띄우는 것을 전제로 합니다. (VCF 9.1 블로그: "These AI Metrics dashboards require enterprises to deploy Grafana".)

| 관측 축 | 무엇을 보는가 | 운영 판단 |
|---------|--------------|----------|
| **Health** | 모델 엔드포인트 가용성, 지연, 복제본 상태 | 다운/포화 감지, 스케일과 롤백 트리거 |
| **Quality** | 검색 품질(유사도 분포)와 응답 품질 신호 | RAG 청크/모델 교체의 회귀 감지 → [7.5](#75-모델-버전과-엔드포인트-관리) |
| **Behavior** | 토큰 사용 패턴, 도구 호출 패턴, 이상 동작 | 비정상 사용, 비용 급증, 프롬프트 인젝션 징후 추적 |

**관측성 데이터 흐름(개념)**

```
PAIS(추론 엔진, KB, 에이전트)
   │  메트릭/트레이스 (OTel)
   ▼
OpenTelemetry Collector ──▶ 메트릭 백엔드(Prometheus 등)
                                   │
                                   ▼
                              Grafana 대시보드
                        (모델 health, quality, behavior)
```

> **전제 조건** — AI 메트릭 대시보드는 조직이 **Grafana를 직접 배포**해야 동작합니다. 즉 관측성은 "켜져 있는" 기능이 아니라 **배포하고 연결해야 하는** 구성입니다. 정확한 메트릭 항목과 대시보드 구성은 적용 직전 [PAIS 릴리스 노트](https://techdocs.broadcom.com/us/en/vmware-cis/private-ai/foundation-with-nvidia/9-1/private-ai-release-notes/vmware-private-ai-services-release-notes.html)와 [VCF 9.1 블로그](https://blogs.vmware.com/cloud-foundation/2026/05/05/streamline-simplify-and-protect-all-your-ai-workloads-with-vcf-9-1/)로 확인하시기 바랍니다.

**PAIS 3.0에서 달라진 것** — Grafana를 직접 배포해야 한다는 전제는 같지만, 3.0은 그 위에 올릴 **예시 Grafana 구성**을 제공하고, 모델과 에이전트 메트릭을 PAIS UI에서 실시간 대시보드로 바로 보여 주며, 추론 백엔드의 헬스를 실시간으로 노출합니다. 2.1에서 "대시보드를 어떻게 구성하나"가 조직의 몫이었다면 3.0은 출발점을 줍니다. 같은 시기에 나온 VCF Operations 9.1.1은 Grafana 대시보드 임포트와 VKS 메트릭의 OpenTelemetry 2초 간격 스트리밍을 더해, 아래 7.4절의 인프라 레벨과 AI 서비스 레벨이 같은 표준(OTel)으로 만납니다.

## 7.4 3계층 모니터링

추론 API 운영은 한 계층만 봐서는 안 됩니다. 문제의 원인이 어느 층인지 분리해야 합니다.

```
앱 레벨 (개발팀)
 • 요청 수 / 응답시간(P50, P95, P99), 에러율(4xx, 5xx), 동시 사용자
AI 서비스 레벨 (PAIS)
 • Model Endpoint 응답시간, 토큰 사용량, Agent 호출 수, 검색 품질(score 분포)
인프라 레벨 (플랫폼팀)
 • GPU 사용률, 메모리, 복제본 상태, 재시작, 네임스페이스 쿼터
```

> 증상-원인 분리 예: "응답이 느리다" → 앱 레벨 P95가 튀는데 PAIS Endpoint 응답시간은 정상이면 **앱/네트워크 문제**, PAIS Endpoint 자체가 느리면 **복제본 부족/GPU 포화**(인프라 레벨 확인). 관측성이 없으면 이 분리가 불가능합니다.

## 7.5 모델 버전과 엔드포인트 관리

사내 추론에서는 모델 교체 시기와 버전을 조직이 직접 결정합니다. 다만 교체 절차를 잘 잡지 않으면 앱 품질이 의도치 않게 바뀔 수 있습니다.

| 항목 | 권장 |
|------|------|
| **모델 식별** | 앱은 `model` 이름을 환경설정(ConfigMap 등)으로 분리. 코드에 하드코딩 금지 |
| **버전 전환** | 새 모델 엔드포인트를 띄워 병행 검증(섀도/카나리) 후 전환. 한 번에 갈아끼우지 않기 |
| **호환성** | 모델 교체 시 프롬프트와 출력 형식이 달라질 수 있음. 회귀 테스트(품질 평가) 필수 |
| **롤백** | 이전 모델 엔드포인트를 일정 기간 유지해 빠른 롤백 경로 확보 |

> AI 앱의 회귀는 "에러"가 아니라 **"답의 품질 저하"** 로 나타납니다. 단위 테스트로는 안 잡힙니다. 모델 교체 전후로 대표 질문 세트에 대한 **정확도와 관련성 평가**를 돌리세요.

## 7.6 비용 — GPU가 핵심

| 비용 요소 | 비중 | 최적화 |
|----------|------|--------|
| **GPU(추론 복제본)** | 가장 큼 | 적정 모델 크기 선택, 자동 스케일링(최소 복제본), 유휴 시 축소 |
| 임베딩과 경량 추론 | 중간 | CPU 추론 엔진 활용 가능(Infinity, llama.cpp). 9.1에선 completion도 CPU(llama.cpp)로 가능 → 경량, PoC는 GPU 절약 |
| 스토리지 | 작음 | Harbor 모델 이미지와 벡터 데이터 |

> **유휴 복제본도 GPU를 점유하면 비용입니다.** 단, 복제본을 0으로 내리면 첫 응답이 느려집니다(Cold Start). 첫 응답 지연(TTFT)이 중요한 사용자 대면 서비스는 **최소 복제본 ≥ 1**, 배치, 내부 작업은 더 공격적으로 축소하는 식으로 워크로드별로 다르게 잡으세요. 상세 스케일링과 HA/DR은 [① 06 6.2절, 6.3절, 6.5절](../../01-infra/docs/06-production.md) 참조.

## 7.8 게이트웨이 메트릭과 캐싱 — 쇼백의 두 번째 원천

7.1절의 `usage` 필드가 호출 단위 신호라면, 게이트웨이 계층([05 5.7절](05-auth-and-gateway.md))을 두었을 때 얻는 것은 **키와 팀 단위로 집계된** 신호입니다. 게이트웨이 메트릭은 최소 다음을 담아야 쇼백과 용량 계획에 쓸 수 있습니다.

| 메트릭 | 단위 | 쓰임 |
|--------|------|------|
| 토큰(프롬프트, 완성) | 키, 팀, 모델 별칭, 연결 방식(로컬, 공유, 원격)별 | 쇼백 배분, 원격 모델 실비 분리 |
| 요청 수와 429 비율 | 키, 팀별 | 예산 초과와 스로틀 발생 추적 |
| 캐시 적중률 | 응답 캐시와 시맨틱 캐시별 | 절감 효과와 캐시 정책 조정 |
| 라우팅과 폴백 횟수 | 별칭별 | 백엔드 장애와 혼용 비율 |
| 게이트웨이 자체 지연 | P95 | 7.4절 3계층 모니터링에서 앱과 PAIS 사이의 한 층 |

이 지표를 VCF Operations의 GPU와 네임스페이스 지표와 합치면 "어느 팀이 어느 모델로 GPU를 얼마나 썼는가"가 한 대시보드에 모입니다([⑦ 05 5.1.1절 showback](../../07-design/docs/05-tenancy-security.md)).

**캐싱의 두 층** — 추론 엔진 쪽의 **프리픽스 캐싱**(같은 앞부분의 계산을 재사용)과 게이트웨이나 앱 쪽의 **응답 캐시**(같은 질문의 답을 재사용)는 다른 층입니다. 앞쪽은 Model Runtime의 엔진 설정에 달려 있어 플랫폼 팀이 켜고 앱은 고정 프리픽스를 프롬프트 앞에 두는 것으로 협조합니다. 어떤 캐싱 옵션이 PAIS Model Runtime에서 노출되는지는 공식 문서로 확인하십시오. 뒤쪽은 게이트웨이나 앱이 구현하며, 사용자 범위 데이터가 든 응답은 캐시하지 않는 조건이 붙습니다. 앱 쪽의 절감 수단은 [앱 가이드 05 5.5절](https://github.com/JaeHoYun/vcf-private-ai-apps/blob/main/docs/05-platform-consumption.md)에 있습니다.

## 7.9 배치 추론 실행 경로와 온라인 우선순위

대량 문서를 일괄 요약, 분류, 추출하는 **배치 추론**은 대화형 서비스와 같은 엔진을 쓰지만 목표가 다릅니다. 지연이 아니라 "이 윈도우 안에 문서 N건"이 목표이고, 그래서 GPU를 높은 가동률로 채울 수 있는 대신 같은 GPU를 쓰는 대화형 서비스의 첫 토큰 지연을 잡아먹기 쉽습니다. PAIS Model Runtime이 공식으로 제공하는 것은 온라인 OpenAI 호환 엔드포인트이며, 추론 엔진의 오프라인 배치 모드를 PAIS 안에서 켜는 경로는 공식 문서에서 확인되지 않습니다. 그래서 실행 경로는 셋으로 갈립니다.

| 경로 | 모습 | 맞는 상황 | 감수하는 것 |
|------|------|-----------|-------------|
| 온라인 엔드포인트 공유 | 배치 드라이버가 대화형 서비스와 같은 모델 엔드포인트를 호출. 드라이버의 동시성을 낮게 고정하고 야간 윈도우에 몰며, 대화형 P95가 기준선을 넘으면 스스로 줄이는 백프레셔 | 배치량이 작거나 야간 유휴 용량으로 충분할 때 | 우선순위를 드라이버의 자제에 의존. 피크 시간에 겹치면 대화형이 느려짐 |
| 배치 전용 엔드포인트 | 같은 모델을 배치용 엔드포인트(별도 레플리카, 필요하면 별도 네임스페이스와 쿼터)로 하나 더 띄움 | 배치가 상시적이거나 대화형의 지연 목표가 엄격할 때 | GPU를 나눠 가져야 하므로 총량이 늘거나 각 풀의 여유가 줄어듦. 야간에는 배치 풀을 대화형에 빌려주는 운영이 필요 |
| PAIS 밖의 자가 오프라인 배치 | 추론 엔진의 오프라인 배치 API를 DLVM이나 VKS Job에서 직접 실행. Model Gallery의 모델을 내려받아 씀 | 수천만 토큰 규모의 일회성 작업, 온라인 엔드포인트가 지원하지 않는 엔진 옵션이 필요할 때 | Model Runtime의 관리, 관측, 인증 밖으로 나가므로 ③의 게이트웨이와 트레이싱이 적용되지 않음. 결과와 로그를 앱이 직접 남겨야 함 |

우선순위를 강제하는 플랫폼 수단은 다음과 같습니다. 네임스페이스 쿼터는 상한이고 GPU Reservation은 하한이므로, 대화형 네임스페이스에 Reservation을 두면 배치가 아무리 몰려도 대화형의 몫은 남습니다([⑤ 02 2.5절](../../05-security/docs/02-network-tenant-isolation.md)). 배치 드라이버 파드에는 Kubernetes PriorityClass를 낮게 주어 노드 압박 시 먼저 밀려나게 할 수 있지만, 모델 엔드포인트 파드는 PAIS가 관리하므로 그 우선순위는 엔드포인트 분리로만 조정합니다. 게이트웨이 계층(5.7절)이 있으면 키 단위 레이트리밋으로 배치 키의 동시성을 제한하는 것이 가장 간단한 집행 지점입니다.

호출 방식도 대화형과 다릅니다. 스트리밍은 끄고, `max_tokens`를 작업에 맞게 고정하며, 문서 단위로 요청을 나눠 실패한 문서만 재시도합니다([03 3.9절](03-openai-compatible-endpoints.md)의 재시도 원칙). 프리픽스 캐싱이 켜져 있으면 지시문을 고정 프리픽스로 두어 같은 앞부분의 계산을 재사용합니다(7.8절). 단가는 가동률이 결정하므로, 야간 유휴 GPU를 채우는 배치는 같은 작업을 피크 시간에 돌리는 것보다 토큰당 비용이 크게 낮습니다([⑥ 07 7.7절](../../06-sizing-cost/docs/07-tco-cost-model.md)). 워크로드 분류와 사이징은 [⑥ 01 1.2절](../../06-sizing-cost/docs/01-sizing-methodology.md), 파이프라인 설계는 [앱 가이드 03 3.7절](https://github.com/JaeHoYun/vcf-private-ai-apps/blob/main/docs/03-design-patterns.md), 운영 규율은 [앱 가이드 14 14.9절](https://github.com/JaeHoYun/vcf-private-ai-apps/blob/main/docs/14-operations.md)에 있습니다.
