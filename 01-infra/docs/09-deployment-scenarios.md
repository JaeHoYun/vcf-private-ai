# 09 — 구축 시나리오

> 기반 버전은 [README 버전 기준 문서](../README.md#기반-버전)를 참조하세요.

같은 PAIF/PAIS를 구축하더라도 **어디서 출발하느냐**에 따라 구축 절차가 크게 달라집니다. 아무것도 없는 곳에 새로 구축하는 것과, 이미 운영 중인 환경에 추가하는 것과, 다른 플랫폼에서 전환하는 것은 밟아야 할 단계도 조심할 것도 다릅니다.

이 문서는 출발 상황을 **세 가지 시나리오**로 나눠 각각의 **선결요건, 절차 골격, 리스크, 의사결정 기준**을 가이드 수준에서 정리합니다. 상세한 단계별 작업계획서가 아니라, "지금 상황에서는 어디서부터, 무엇을 조심하며 시작하나"를 정하기 위한 안내서입니다.

> **이 문서의 경계:** 구축의 *출발 시나리오*만 다룹니다. 상세 사이징은 [⑥ 사이징, 용량, 비용 가이드](../../06-sizing-cost/README.md), 보안 베이스라인은 [⑤ 보안과 거버넌스 가이드](../../05-security/README.md), 구축 *이후*의 운영과 업그레이드(Day-2)는 [문서 10](10-operations.md)에서 다룹니다.

> **선수지식:** 아래 개념을 가볍게 알아 두면 이 문서를 읽기 수월합니다. 모르면 아래 '모를 때'의 참고경로를 먼저 확인하세요.

| 영역 | 알아두면 좋은 것 | 모를 때 |
|---|---|---|
| VCF 구성 | SDDC Manager, 관리 도메인과 워크로드 도메인의 분리 구조 | [A1 용어집](../appendix/A1-appendix.md) + [02 아키텍처](02-architecture.md) |
| GPU 워크로드 도메인 | GPU-Accelerated Workload Domain이 일반 도메인과 분리하고 공존하는 방식 | [A1 용어집](../appendix/A1-appendix.md) + [02 아키텍처](02-architecture.md) |
| 출발 상황 구분 | 그린필드, 브라운필드, 마이그레이션의 의미 차이 | [A1 용어집](../appendix/A1-appendix.md) + [01 개념](01-concepts.md) |
| VCF 편입 경로 | Import(가져오기)와 Convert(전환)로 기존 vSphere를 워크로드 이전 없이 편입 | [A1 용어집](../appendix/A1-appendix.md) + [02 아키텍처](02-architecture.md) |
| 워크로드 이전 | Workload Mobility로 VM을 재부팅 없이 대량 이전하는 개념 | [A1 용어집](../appendix/A1-appendix.md) |
| 라이선스와 사이징 선결 | NVAIE(NVIDIA AI Enterprise) 필요 여부, 용량 사이징을 착수 전에 확정해야 하는 이유 | [A1 용어집](../appendix/A1-appendix.md) + [01 개념](01-concepts.md) |

> 시나리오를 정한 뒤 실제 프로젝트로 착수할 때 확인할 현황 항목과 작업기술서(SoW)에 담을 기준은 [9.6절](#96-착수-전-현황-파악-기준)과 [9.7절](#97-작업기술서sow-정의-기준)에 정리했습니다.

## 9.1 세 가지 구축 시나리오. 무엇을 고를까

| 시나리오 | 한 줄 설명 | 출발 상태 | 대표 상황 |
|---------|-----------|----------|----------|
| **신규 구축** (그린필드) | 백지에서 처음부터 구축함 | VCF 없음 | 신규 데이터센터, PoC 전용 클러스터 |
| **기존 환경에 추가 구축** (브라운필드) | 운영 중인 VCF/vSphere에 AI만 추가 | VCF 또는 vSphere 운영 중 | 기존 가상화에 AI 인프라만 증설 |
| **전환** (마이그레이션) | 타 플랫폼에서 VCF로 전환하며 구축 | 경쟁사 가상화 운영 중 | 타사 플랫폼 → VCF 표준화 |

> **용어 참고:** 그린필드(아무것도 없는 백지)와 브라운필드(기존 환경 기반)는 인프라 업계에서 사용하는 표현입니다. "레드필드" 같은 표현은 표준이 아니며, 경쟁사 플랫폼을 교체하는 경우는 **마이그레이션**(전환)으로 부릅니다.

**간단 의사결정:**

- 기존에 VMware vSphere 또는 VCF를 사용하고 있나? → 아니오면 **신규**, 예면 **브라운필드**
- 타사 하이퍼바이저나 컨테이너 가상화 플랫폼에서 전환하나? → **전환**
- 셋은 배타적이지 않습니다. 예컨대 타사에서 전환하면서 신규 클러스터를 일부 새로 구축하는 혼합도 흔합니다.

## 9.2 신규 구축 (그린필드)

가장 단순한 경로입니다. VCF부터 PAIF/PAIS까지 정해진 순서로 구축합니다.

- **절차 골격:** [문서 02 2.6절 구축 Phase 개요](02-architecture.md)가 기준 문서입니다(여기서 반복하지 않음). 요약하면 **VCF 9.1.x → PAIF(GPU) Workload Domain → Harbor/DSM → PAIS 3.0 → 카탈로그** 순입니다. PAIS 3.0부터는 배포 시점에 Agent Builder와 Data Indexing 모듈을 개별로 켜고 끌 수 있으므로, 모델 서빙만 필요한 그린필드라면 두 모듈을 끄고 시작해 필요할 때 켜는 편이 초기 자원과 운영 범위를 줄입니다.
- **신규 구축 추가 점검:** 초기 용량은 [⑥], 보안 베이스라인은 [⑤]를 *처음 설계에 반영*하면 나중 재작업이 줄어듭니다. 네임스페이스와 네이밍 표준은 초기에 확정하세요(가동 후 바꾸기 어렵습니다).
- **리스크:** 상대적으로 낮습니다. 다만 **GPU 하드웨어 호환성(BCG=Broadcom 호환성 가이드 / HCL=하드웨어 호환성 목록)** 과 라이선스(NVAIE 필요 여부, [문서 01 1.2절](01-concepts.md))를 착수 전 반드시 확인합니다.

## 9.3 기존 환경에 추가 구축 (브라운필드)

이미 vSphere나 VCF를 운영 중인 곳에 PAIF/PAIS를 추가하는 경우입니다. 출발점에 따라 두 갈래입니다.

### (A) 이미 VCF를 운영 중. GPU 워크로드 도메인 추가

기존 VCF에 **GPU-Accelerated Workload Domain**(GPU 가속 워크로드 도메인)을 새로 만들고 그 도메인에 PAIS를 설치합니다. 기존 일반 업무 워크로드와는 도메인 단위로 분리한 채 공존합니다.

- **선결:** 기존 VCF가 9.1 호환 버전인지 확인 → 미달이면 PAIF 추가 *전에* 먼저 업그레이드(아래 박스).
- GPU 호스트 증설, NSX, 스토리지(vSAN) 가용 용량 확인.
- **기존 VKS 클러스터 점검(VCF 9.1.1 / VKS 3.7):** TanzuKubernetesCluster(TKC) API로 만든 구형 클러스터는 VKS 3.7에서 지원이 끝났고(VKr 1.32가 마지막), VKS 3.7은 VKr 1.32 자체를 지원하지 않습니다. 기존 VKS 클러스터가 있다면 ClusterClass 기반으로 전환하고 VKr 1.33 이상으로 업그레이드한 뒤에 PAIS 3.0을 설치합니다([문서 10 10.1.1절](10-operations.md)).

### (B) VCF 없이 vSphere만 운영 중. 먼저 VCF로 편입

VCF 9는 기존 vSphere를 **워크로드 이전 없이** VCF로 편입하는 두 경로를 제공합니다(기존 구성과 가동 중 워크로드를 보존하므로 이전 리스크가 낮습니다).

| 경로 | 언제 | 무엇을 하나 |
|------|------|------------|
| **Convert(전환)** | 아직 VCF 인스턴스가 없고, 기존 vCenter, NSX, Operations만 있을 때 | 기존 구성요소로 VCF 관리 도메인을 구성하고, 누락된 컴포넌트는 자동 배포 |
| **Import(가져오기)** | 이미 VCF가 있을 때 | 기존 vSphere를 추가 VI 워크로드 도메인으로 편입(누락된 NSX 등 자동 배포) |

편입이 끝나면 (A)와 동일하게 GPU 워크로드 도메인 추가로 진행합니다.

> 기존 자산의 인벤토리와 Convert, Import 경로별 통합 판단(버전 하한 포함)은 [⑦ 08 브라운필드 통합 설계 8.1절, 8.3절](../../07-design/docs/08-brownfield-integration.md)이 상세 기준입니다. 이 절은 출발 상황별 절차 골격만 다룹니다.

> **업그레이드는 여기서가 아니라 운영(Day-2)에서 다룹니다.** 기존 VCF가 9.1 미만이면 PAIF 추가 전 업그레이드가 필요합니다. 9.0.x → 9.1 한눈 체크리스트는 [문서 00](00-whats-new.md)의 0.6절에 있고, 순서와 롤백을 포함한 상세 업그레이드 런북은 [문서 10 10.1절](10-operations.md)에서 다룹니다(업그레이드는 *이미 운영 중인 플랫폼의 라이프사이클 관리*이므로 Day-2 운영에 속합니다).

- **리스크:** 기존 운영 워크로드에 미치는 영향(유지보수 창 필요), 버전과 하드웨어 호환, 기존 네트워크/스토리지 자원 잠식.

> **적용 전 확인:** VCF의 Convert/Import 두 경로와 기존 VCF에 GPU 워크로드 도메인을 추가하는 방식은 공식 문서 기준입니다. 다만 9.1의 정확한 절차와 전제조건은 적용 전 [Broadcom TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/private-ai/foundation-with-nvidia/9-1.html)로 재확인하시기 바랍니다 ([기존 vSphere의 VCF 9 편입 — VCF 블로그](https://blogs.vmware.com/cloud-foundation/2026/02/05/how-to-converge-a-vmware-vsphere-environment-to-vmware-cloud-foundation-9-0/), [GPU 가속 워크로드 도메인 배포 — TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/private-ai/foundation-with-nvidia/9-0/private-ai-foundation-9-x/deploying-private-ai-foundation-with-nvidia/deploy-a-vi-workload-domain-in-vmware-cloud-foundation.html)).

## 9.4 전환. 경쟁사에서 이전 (개요)

타사 하이퍼바이저나 컨테이너 가상화 플랫폼에서 VCF로 전환하며 PAIF/PAIS를 구축하는 시나리오입니다. **본 절은 개요와 골격**이며, 상세 전환 플레이북은 후속 작업 또는 별도 가이드 후보입니다. 이전할 자산별 통합 판단은 [⑦ 08 브라운필드 통합 설계](../../07-design/docs/08-brownfield-integration.md)를 참조합니다.

**골격 단계:**

1. **평가(자산 인벤토리):** 이전할 VM, 데이터, GPU 워크로드를 식별하고 호환성과 의존성을 파악([⑦ 08 8.1절](../../07-design/docs/08-brownfield-integration.md))
2. **착지 환경 준비:** 신규(9.2절) 또는 브라운필드(9.3절)로 목표 VCF 환경을 먼저 구축
3. **워크로드 이전:** **VCF Operations Workload Mobility**(구 HCX)로 vSphere, 비vSphere VM을 재부팅 없이 대량 이전
4. **병행 운영과 컷오버:** 단계적으로 이전하며 검증 후 전환, 롤백 경로 확보
5. **AI 재구성:** 모델, Knowledge Base, 에이전트는 단순 VM 이전과 별개로 ①의 구축과 개발 절차([문서 03](03-workflows.md))로 재구성

> **전환 동인(맥락):** vSphere 8은 2027년 10월 일반 지원 종료가 예고되어, 플랫폼 현대화 시점 판단에 참고할 수 있습니다.

> **적용 전 확인:** Workload Mobility의 비vSphere(경쟁사) 소스 지원 범위와 제품 명칭은 변경이 잦으므로 적용 전 공식 문서로 확인하시기 바랍니다. 경쟁사 고유의 전환 도구와 절차는 본 가이드 범위 밖입니다 ([VCF Operations Workload Mobility — VMware](https://www.vmware.com/products/cloud-infrastructure/vcf-operations-workload-mobility)).

## 9.5 시나리오 비교 + 공통 선결요건

| 항목 | 신규(그린필드) | 기존 환경에 추가 구축(브라운필드) | 전환(마이그레이션) |
|------|:---:|:---:|:---:|
| 출발 상태 | 백지 | 기존 VCF/vSphere | 타 플랫폼 |
| 난이도와 리스크 | 낮음 | 중간(기존 영향) | 높음(이전과 컷오버) |
| 핵심 도구 | VCF 설치 | VCF Import/Convert + GPU WD | Workload Mobility |
| 워크로드 이전 | 없음 | 없음(편입) | 있음 |
| 대표 리스크 | 하드웨어 호환 | 운영 영향과 다운타임 | 데이터 이전과 컷오버 |

**공통 선결요건 체크리스트:**

```
- GPU 하드웨어 BCG/HCL 호환 확인 (특히 Blackwell, ConnectX-7/BlueField-3)
- 라이선스 확인 (VCF, NVAIE 필요 여부) → 문서 01 1.2절
- 용량 사이징 → ⑥ 사이징, 용량, 비용 가이드
- 보안 베이스라인 → ⑤ 보안, 거버넌스 가이드
- 네임스페이스, 네이밍 표준 사전 확정
- (브라운필드, 전환) 유지보수 창 + 롤백 계획 수립
```

## 9.6 착수 전 현황 파악 기준

시나리오를 고른 뒤에는 착수 회의 전에 현황을 실측합니다. 아래 공통 항목은 세 시나리오 모두에 적용되고, 시나리오별 항목은 해당 시나리오에서만 추가로 확인합니다. 필수 항목은 착수와 범위 산정에 반드시 필요한 입력, 권장 항목은 설계 확정 전에 확인할 입력, 조건부 항목은 해당될 때만 확인할 입력입니다.

| 공통 항목 | 왜 필요한가 | 필수도 |
|---|---|:---:|
| 사업 목표와 성공 기준 | SoW 범위와 인수 기준의 출발점 | 필수 |
| 대상 AI 워크로드(추론, RAG, 파인튜닝, 에이전트) | 사이징, PAIS 구성, GPU 종류 결정 | 필수 |
| GPU 타깃 모델과 수량 | BCG/HCL 호환 확인과 조달 근거 | 필수 |
| 라이선스 보유 현황(VCF 구독, NVAIE) | 선결요건([01 1.2절](01-concepts.md)) | 필수 |
| 네트워크, DNS, IP 대역, 인터넷 경로(에어갭 여부) | 모델 다운로드, Harbor, Endpoint 노출 | 필수 |
| 사이징 산정값 | [⑥ 사이징 결과](../../06-sizing-cost/README.md) 인용 | 필수 |
| 예상 사용자와 테넌트 수 | 멀티테넌시와 쿼터 설계 | 권장 |
| 보안과 컴플라이언스 요건(규제, 망분리, 암호화) | [⑤ 보안 베이스라인](../../05-security/README.md) 반영 | 권장 |
| 네임스페이스와 네이밍 표준 | 가동 후 변경이 어려우므로 초기에 확정 | 권장 |
| 식별과 인증(IdP, SSO) 연동 대상 | Identity Broker 연계 | 조건부 |

| 시나리오 | 추가로 확인할 항목 |
|---|---|
| 신규(그린필드) | 상면, 전력, 냉방, 랙 중량. GPU 서버와 NIC의 조달 상태와 리드타임. 물리 네트워크 패브릭. vSAN 디스크 구성. 초기 노드 수와 확장 여지 |
| 브라운필드 | 운영 제품과 버전, 9.1 호환 여부, (A)와 (B) 갈래 판정. 기존 도메인과 클러스터 목록. 여유 용량(코어와 RAM, vSAN 가용 용량, NSX Edge와 IP 풀). 기존 네이밍 규칙. 운영 워크로드의 중요도와 영향 범위. 유지보수 창과 변경관리 승인 경로. 기존 VKS 클러스터의 API 유형(TKC, ClusterClass)과 VKr 버전. (B) 갈래는 Convert와 Import 중 경로와 누락 컴포넌트 |
| 전환(마이그레이션) | 소스 플랫폼과 버전. 이전 대상 VM 수, 총 vCPU와 RAM, 데이터 총량과 증가율. GPU 워크로드 유무. VM 간 의존성과 통신 관계. IP 재지정 필요 여부. Workload Mobility의 소스 호환 여부. 전송 대역폭과 전송 창. 컷오버 중단 허용 시간. 병행 운영 기간과 전환 기준. 재구성할 AI 자산(모델, 지식베이스, 에이전트, 파이프라인). 소스 고유 기능 의존 |

실측 결과는 다음 기준으로 관리합니다.

- **미충족 항목은 선결요건으로 등록합니다.** 실측에서 확인되지 않거나 준비되지 않은 항목은 담당, 기한, 상태(완료, 진행, 미착수)를 붙여 선결요건 목록으로 관리합니다. 착수일까지 해소되지 않는 선결요건은 SoW의 전제나 선행작업으로 명시합니다.
- **시나리오별 선결요건을 9.5절 공통 목록에 더합니다.** 브라운필드는 9.1 미만 환경의 선행 업그레이드([00 0.6절](00-whats-new.md), [10 10.1절](10-operations.md)), 구형 VKS 클러스터의 ClusterClass 전환과 VKr 1.33 이상 선행([10 10.1.1절](10-operations.md)), 여유 용량 확인이나 GPU 호스트 증설, 유지보수 창 확정, 롤백 계획, Convert와 Import 전제조건 확인을 추가합니다. 전환은 착지 환경 결정, Workload Mobility 호환과 라이선스, 의존성 매핑, 전송 방식과 창, 컷오버와 병행 운영 기준, AI 자산 재구성 계획([03](03-workflows.md))을 추가합니다.
- **혼합 시나리오는 전환을 기준으로 정리합니다.** 전환하면서 일부 클러스터를 신규로 구축하는 경우, 전환 항목을 기준으로 삼고 착지 환경 부분에 신규나 브라운필드 항목을 더합니다.

## 9.7 작업기술서(SoW) 정의 기준

작업기술서(SoW, Statement of Work)는 무엇을, 어디까지, 누가, 언제까지 하고, 무엇을 달성하면 완료로 판단할지를 확정하는 문서입니다. 범위 분쟁과 재작업을 줄이는 착수와 계약의 기준선입니다. 시나리오와 무관하게 아래 여덟 요소를 담고, 시나리오별로 달라지는 부분을 반영합니다.

| 요소 | 작성 기준 | 시나리오별로 달라지는 부분 |
|---|---|---|
| 범위 | 포함 범위와 제외 범위를 함께 적습니다. 제외 범위를 미리 적어야 범위 분쟁을 예방할 수 있습니다 | 공통 제외: 앱과 모델 자체 개발, 상세 사이징(⑥ 선행), Day-2 운영([10](10-operations.md)). 브라운필드는 기존 워크로드 이전을, 전환은 앱 리팩터링과 소스 고유 도구를 제외 범위에 명시 |
| 산출물 | 구성서(As-built), 검증 리포트, 운영 인계 자료(계정, 접속, 런북 위치)를 기본으로 하고 산출물마다 검수자를 지정합니다 | 브라운필드는 편입 결과와 기존 구성 영향 기록, 전환은 자산 인벤토리와 의존성 맵, 이전 계획서와 컷오버 런북을 추가 |
| 작업분해(WBS) | 단계마다 완료 조건을 측정 가능한 상태로 적습니다(예: Endpoint 추론 200 OK) | 아래 작업분해 표 참조 |
| 전제와 고객 책임 | 틀리면 일정과 범위가 바뀌는 전제(라이선스와 GPU 확보, ⑤⑥ 선행 확정)와 발주측 책임(상면, 네트워크, IdP, 방화벽 협조, 검수 인력)을 분리해 적습니다 | 브라운필드는 유지보수 창 승인과 변경관리 경로, 전환은 소스 접근 권한과 컷오버 창 승인 |
| 역할과 책임 | 주요 작업마다 책임, 승인, 협의, 통보 주체를 정합니다([⑦ 09 RACI](../../07-design/docs/09-roles-raci.md)) | 브라운필드는 변경관리, 전환은 이전과 컷오버의 승인 주체를 별도 지정 |
| 마일스톤 | 착수, 기반 완료, PAIS 가동, 인수 완료를 기본으로 합니다 | 브라운필드는 유지보수 창, 전환은 이전 배치와 컷오버 창에 맞춤 |
| 인수 기준 | 완료 판단 조건을 점검 가능한 문장으로 적습니다 | 아래 인수 기준 표 참조 |
| 리스크와 롤백 | 리스크마다 영향, 완화 방안, 롤백 방법을 함께 적습니다 | 아래 대표 리스크 표 참조 |

**작업분해 골격**

| 시나리오 | 단계와 완료 조건 |
|---|---|
| 신규 | VCF 9.1.x 배포(코어 헬스 정상), GPU 워크로드 도메인과 GPU Operator(GPU 인식, 해당 시 MIG), Harbor와 DSM(이미지와 모델 push, pull), PAIS 3.0 설치(Endpoint 추론 200 OK), 카탈로그 게시, 검증과 인계(인수 기준 충족) |
| 브라운필드 | (선행) 9.1 업그레이드, (B 갈래) Convert 또는 Import(기존 워크로드 보존과 편입 완료), GPU 워크로드 도메인 추가, PAIS 3.0 설치, 카탈로그 게시, 기존 워크로드 회귀를 포함한 검증과 인계 |
| 전환 | 평가(이전 목록 확정), 착지 환경 구축(신규나 브라운필드 절차), Workload Mobility 대량 이전, 병행 운영과 단계 컷오버(롤백 경로 확보), AI 자산 재구성(추론 200 OK) |

**인수 기준**

| 시나리오 | 완료로 판단하는 조건 |
|---|---|
| 공통 | 코어 헬스 정상(SDDC Manager, vCenter, NSX, Supervisor READY=True). GPU 인식과 메트릭 대시보드 정상. PAIS Endpoint 추론 200 OK와 트레이스 수신. ⑤ 보안 베이스라인 점검 통과. 구성서와 인계 자료 제출 |
| 브라운필드 | 공통 조건에 더해 기존 운영 워크로드 무영향 회귀 확인. (B 갈래) 편입 후 기존 워크로드 정상 |
| 전환 | 이전 VM 정상 가동, 데이터 일관성 검증 통과, AI 자산 재가동, 롤백 경로 검증 완료 |

**대표 리스크**

| 시나리오 | 리스크 | 완화 | 롤백과 비상 대응 |
|---|---|---|---|
| 신규 | GPU 하드웨어 비호환 | 착수 전 BCG/HCL 확정 | 대체 모델 검토 |
| 신규 | 조달 리드타임 | 발주 선행, 일정 버퍼 | 축소 PoC 우선 진행 |
| 신규 | 사이징 과소 | ⑥ 재검토 | 노드 증설 여지 확보 |
| 브라운필드 | 기존 운영 영향과 다운타임 | 유지보수 창 내 작업, 사전 공지 | 변경 롤백 |
| 브라운필드 | 여유 용량 부족 | 사전 확인, 증설 | 도메인 분리 |
| 브라운필드 | (B 갈래) 편입 실패 | 전제조건 확인과 백업 선행 | 편입 롤백과 재시도 |
| 전환 | 데이터 이전 실패나 손상 | 사전 백업, 단계 이전, 검증 | 소스 보존, 재이전 |
| 전환 | 컷오버 다운타임 초과 | 병행 운영, 창 산정, 리허설 | 병행 운영으로 롤백 |
| 전환 | 의존성 누락 | 의존성 맵 선행 | 관련 VM 그룹 재이전 |
| 전환 | Workload Mobility 호환 한계 | 착수 전 호환 확인 | 대체 이전 방식 |

SoW를 합의할 때는 선택한 시나리오와 갈래, 결정 근거, 미해결 선결요건, SoW 버전과 일자, 작성자(인프라와 아키텍트), 검토자(보안과 사이징), 승인자(사업과 PM)를 함께 기록합니다. 미해결 선결요건이 남은 채 승인하면 그 항목은 SoW의 전제로 명시합니다.
