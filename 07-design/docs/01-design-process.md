# 01 — 설계 프로세스와 요구사항 수집

[← 목차로](../README.md)

좋은 Private AI 설계는 제품 기능에서 시작하지 않습니다. **요구사항과 제약(결정 요인)** 에서 시작해, 그 결정 요인이 어떤 설계 결정을 어느 방향으로 좌우하는지를 추적합니다. 이 문서는 결정 요인을 수집하는 방법과 결정의 순서를 정합니다.

> 본 문서의 수치와 동작은 작성 시점(2026-06, 9.1.1과 PAIS 3.0 GA 반영 2026-09) VCF 9.1.1 / PAIF 9.1.1 / PAIS 3.0 기준이며, 적용 전 공식 문서로 재확인하시기 바랍니다.

---

## 1.1 설계 프로세스 개요

```
요구사항, 제약 수집(결정 요인) →  결정 요인이 좌우하는 설계 결정 식별
   →  설계 결정별 경로 선택(06 카탈로그)  →  가장 가까운 블루프린트 선택, 조정(02)
   →  설계 결정 기록으로 선택, 근거 남기기(06.3) →  설계 리뷰, 검증 관문(07)
```

핵심은 **결정 요인이 결정을 좌우한다**는 점입니다. 설계 결정 카탈로그([06](06-decision-forks.md))는 결정의 관점에서, 이 문서는 요구사항의 관점에서 같은 결정 요인-설계 결정 대응 관계를 다룹니다.

## 1.2 결정 요인 수집

아래 여덟 가지를 먼저 수집합니다. 결정 요인마다 무엇을 확인하는지, 어디서 확인하는지, 결정 전에 반드시 필요한지, 어떤 결정(D1–D16)을 강하게 좌우하는지를 함께 정리했습니다.

| 결정 요인 | 무엇을 확인하나 | 확인 출처 | 필수도 | 강하게 좌우하는 결정 |
|---------|----------------|----------|:---:|-----------------|
| 워크로드 프로파일 | 추론/학습/RAG/에이전트 비중, 모델 크기, 동시 사용자와 요청 | 업무팀 인터뷰, 기존 사용량 | 필수 | D2 GPU 공유, D3 서빙 배치, D4 서빙 방식, 에이전트가 쓰기까지 하면 D15 가드레일 배치, D16 자율성 상한 |
| 성능 SLO | 첫 토큰 지연(TTFT), E2E 지연 목표, 처리량(토큰/초) | 업무 요구, 벤치마크 | 필수 | D2 GPU 공유, D4 서빙 방식, D9 가용성 |
| 규제와 데이터 주권 | 에어갭 의무, 격리 등급, 감사와 접근 통제 요건, 보호 문서 등급 | 보안, 컴플라이언스 담당 | 필수 | D12 에어갭, D10 테넌시, D11 Identity, D14 보호 문서 인입 |
| 예산 | CapEx/OpEx 한도, 최소 호스트 수, 라이선스 예산 | 구매, 재무 담당 | 필수 | D1 토폴로지, D2 GPU 공유 |
| 기존 인프라 자산 | 물리망(VLAN), SAN/NAS 투자, GPU 보유, NVAIE 라이선스 | 인프라 실사 | 권장 | D5 네트워킹, D6 LB, D7 스토리지 |
| 운영 스킬셋 | NSX, 쿠버네티스, 스토리지 운영 역량 | 팀 역량 평가(상, 중, 하) | 권장 | D3 서빙 배치, D5 네트워킹, D8 VectorDB |
| 멀티테넌시 요건 | 테넌트 수, 신뢰 경계, 셀프서비스 필요, 사업부별 차지백과 토큰 예산 | 조직 구조, 사업부 요구 | 권장 | D10 테넌시, D5 네트워킹, D13 AI 게이트웨이 계층 |
| 가용성과 연속성 | 허용 RPO/RTO, 사이트 수, 무중단 요구 | 사업 연속성 계획 | 권장 | D9 가용성과 DR, D2 GPU 공유(HA 제약) |

> 결정 요인은 "있으면 좋은 것"이 아니라 **수치와 등급으로** 적어야 결정의 근거로 삼을 수 있습니다. 예: "지연 빠르게"가 아니라 "TTFT P95 1.5초 이하".

결정 요인 목록을 실제 프로젝트에서 관리할 때는 다음 기준을 적용합니다.

- **필수 항목부터 확정합니다.** 필수 네 가지(워크로드 프로파일, 성능 SLO, 규제와 데이터 주권, 예산)가 비어 있으면 D1, D2처럼 되돌리기 어려운 결정을 내리지 않습니다.
- **모르는 값은 미확인 목록으로 관리합니다.** 값을 추정해 채우지 않고 "확인할 항목, 담당, 기한"을 적은 미확인 목록에 등록합니다. 미확인 항목이 좌우하는 결정은 보류합니다.
- **출처를 함께 남깁니다.** 값마다 어디서 얻었는지(인터뷰, 사용량 로그, 계약서)를 적어야 리뷰에서 근거를 검증할 수 있습니다([07 7.2절](07-design-review.md) Gate 0).
- **전제가 바뀌면 갱신합니다.** 예산, 규제, 사용자 규모가 바뀌면 해당 요인을 갱신하고, 그 요인이 좌우하는 결정의 재검토 트리거([06 6.3절](06-decision-forks.md#63-결정을-왜-그렇게-정했는지-남기기))를 확인합니다.

## 1.3 설계 결정 순서

의존성이 있는 순서로 결정합니다. 앞 결정이 뒤 결정의 선택지를 좁히기 때문입니다.

1. **D1 토폴로지** — 표준이 기본(통합은 비권고). 설치 시 확정되므로 가장 먼저.
2. **D2 GPU 공유** — 하드웨어 선정(MIG 지원 여부)에 종속됨.
3. **D3, D4 서빙(배치와 방식)** — 워크로드 프로파일을 직접 반영.
4. **D5, D6 네트워크, LB** — 셀프서비스와 VPC 여부가 LB 선택에 영향.
5. **D13 AI 게이트웨이 계층** — LB(0계층) 후단의 별도 계층이므로 D6 다음에. 팀 수와 차지백 요구를 반영.
6. **D7, D8 스토리지, VectorDB** — 기존 자산과 RAG 규모.
7. **D9 가용성과 DR** — 사이트와 링크 요건, GPU HA 제약 반영.
8. **D10–D12 테넌시, Identity, 에어갭** — 규제와 조직 경계.
9. **D14 보호 문서 인입** — D8 VectorDB와 D12 에어갭이 정해진 뒤. 문서 등급과 복호화 존 배치([05 5.4절](05-tenancy-security.md)).
10. **D15, D16 가드레일 배치, 에이전트 자율성 상한** — 유스케이스의 위험 등급이 확정된 뒤. D13의 1계층 게이트웨이 유무가 가드레일 삽입 지점을 좌우.

각 결정은 [06 카탈로그](06-decision-forks.md)에서 경로를 고르고 [06.3 설계 결정 기록 템플릿](06-decision-forks.md)으로 근거를 남깁니다.

## 1.4 이 단계의 산출물

- 수치와 등급으로 확정한 **결정 요인 목록**(1.2)과 미확인 항목 목록
- 가장 가까운 **블루프린트 선택**([02](02-reference-blueprints.md))과 조정 메모
- 결정별 **설계 결정 기록**([06 6.3절](06-decision-forks.md#63-결정을-왜-그렇게-정했는지-남기기))
